Architecture & Design: The Big Picture

🖥️ Point to your screen/diagram while speaking.

"Let's look at how the system is structured. I've followed a decoupled architecture where the automation server and the application server live in a secure VPC."

GitHub → Jenkins → Docker Hub → AWS EC2 → Live App

How the Pieces Fit Together

GitHub acts as our source of truth — every push triggers the entire pipeline automatically. Jenkins is the engine, listening for changes and executing each stage. Docker Hub is our artifact registry, storing versioned and immutable images. AWS EC2 hosts the final running application inside a hardened VPC.

Infrastructure as Code with Terraform

Instead of clicking buttons in the AWS Console, I modularized my infrastructure. This means I can tear down and rebuild this entire environment in minutes with a single command.

HCL · terraform/modules/vpc/main.tf 
// "This module ensures our network is isolated and secure."
module "vpc" {
  source         = "./modules/vpc"
  vpc_cidr       = var.vpc_cidr
  public_subnets = var.public_subnets
}

The Pipeline: Code to Production

❤️ This is the heart of your project. Spend the most time here.

"The heart of the project is the Jenkinsfile — this is our 'Pipeline-as-Code'. I've designed it with six critical stages that take the code all the way from a developer's push to a live, running container in AWS."

01
Checkout

Pull the latest code from the GitHub repository. This is our starting point — always working from the most recent source of truth.

02
Install

Use npm ci for clean, predictable dependency installation — no surprises from mismatched package versions.

03
Test

Run unit tests with Jest. If a single test fails, the pipeline stops immediately. We never ship broken code to production.

04
Docker Build

Package the application into a lightweight, immutable container image. The app and all its dependencies are sealed in one portable unit.

05
Push

Securely upload the versioned image to Docker Hub. This acts as our artifact registry — every build has a unique, traceable version tag.

06
Deploy

SSH into the production EC2 server, pull the new image, and swap containers with zero downtime. The old version stays live until the new one is ready.

04 · 3 min

Security: Protecting the Pipeline

🛡️ Examiners love security. Speak slowly and confidently here.

"Security wasn't an afterthought. I've implemented three layers of protection — at the secret level, at the network level, and at the validation level."

🔐
Secrets Management

No hardcoded passwords — ever. AWS Secrets Manager stores Jenkins credentials. The Jenkins Credentials Store manages SSH keys securely. Nothing sensitive touches the codebase.

🔒
Network Hardening

Terraform enforces strict Security Group rules. Only a specific, allowlisted IP address can access the Jenkins dashboard. The application server is not publicly exposed.

✅
Pre-Deploy Validation

A custom validate-security.sh script checks for common misconfigurations before we ever touch the cloud — a safety net before provisioning begins.

HCL · Security Group Validation 
// "I've added validations to prevent accidental public exposure."
validation {
  condition     = !contains(var.allowed_ips, "0.0.0.0/0")
  error_message = "allowed_ips cannot be 0.0.0.0/0 for security reasons."
}

07 · Q&A

Common Defense Questions

❓ Memorize these. They will almost certainly be asked.
Q1

Why did you choose Docker over deploying the app directly on EC2?

Answer: Docker guarantees environment consistency. If it works on my laptop, it will work on AWS — it completely eliminates the classic "works on my machine" problem. It also makes the deployment process faster and more portable; if I need to move to a different server or cloud provider, I just pull the same image.
Q2

What happens if a build fails mid-pipeline?

Answer: The pipeline fails immediately at the failing stage and sends a notification. It never touches the production server. The old, working version stays online — users experience zero service interruption while the team investigates and pushes a fix.
Q3

Why Terraform instead of just using the AWS Console?

Answer: Two reasons: Reproducibility and Version Control. With Terraform, I can destroy and recreate the entire infrastructure in minutes with one command. And since it's code, infrastructure changes are tracked in Git — I can see who changed what, when, and why. The AWS Console gives you none of that.
Q4

How did you handle sensitive credentials like Docker Hub passwords and SSH keys?

Answer: I never hardcode secrets in the Jenkinsfile or any config file. Docker Hub credentials are stored in the Jenkins Credentials Store and injected at runtime as environment variables. SSH keys for EC2 access are also managed through Jenkins credentials. For cloud-level secrets, I used AWS Secrets Manager.
Q5

What is the difference between Continuous Delivery and Continuous Deployment?

Answer: Continuous Delivery means every passing build is ready to deploy, but a human approves the final push to production. Continuous Deployment means every passing build is automatically deployed to production with no human gate. My pipeline implements Continuous Deployment — once all stages pass, the new version is live automatically.
Q6

What would you improve if you had more time?

Answer: I would add SonarQube for static code analysis and quality gates, move to an Auto Scaling Group with a Load Balancer for high availability, and integrate Slack notifications so the team gets instant feedback on every build. Long term, I'd explore migrating to Kubernetes (EKS) for better orchestration and scalability.
🎯 Final Tip

If you get a question you don't know — don't guess. Say: "That's a great question. I didn't implement that in this version, but the way I would approach it is..." Examiners respect honesty and forward thinking far more than a wrong confident answer.
